### 핵심 사용자 시나리오

**시나리오 1 : 단일 문서 적재 → 위키 페이지 자동 생성**

* ID : SC-001

* 상황 : 흩어져 있던 개발 산출물(요구사항 명세, 설계 메모 등)을 처음으로 위키에 등록할 때

* 목표 : 원본 문서를 멀티 에이전트 파이프라인에 통과시켜, SDLC 단계·도메인에 맞게 분류된 위키 페이지를 자동으로 생성한다

* 사전 조건 : 백엔드/프론트엔드 구동 중, 적재 대상 마크다운 문서가 소스 폴더(또는 URL/붙여넣기)로 접근 가능, 동일 내용 페이지가 아직 위키에 없음

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| -- | ------ | ------ | -- |
| 1 | `적재/소스 입력` 화면에서 파일 브라우저로 문서를 선택하고 충돌 정책 `llm_merge` 선택 후 "분석 시작" 클릭 | `POST /api/ingest`로 run 생성, `run_id` 발급 후 워크플로우 뷰(`/runs/{run_id}`)로 이동 | 충돌 정책 4종 중 선택 |
| 2 | 워크플로우 뷰에서 13단계 노드 진행 상황을 실시간으로 확인 | SSE(`/api/runs/{run_id}/events`)로 노드별 상태(대기/진행/완료/실패) 스트리밍 | React Flow 시각화 |
| 3 | 노드 클릭하여 입력/출력 상세 확인 | fetch→parse→normalize(단계 분류)→decompose→chunk→embed→similarity→merge→verify→crossref→index→log 순차 실행, 신규 페이지 생성 | LLM 호출 노드 배지 표시 |
| 4 | 완료 후 "페이지 →" 링크 클릭 | `wiki/100-요구사항/130-고객관리/132-고객검색/고객-검색.md` 생성, 위키 뷰어로 이동 | frontmatter+본문 저장 |

* 입력 예시

```markdown
# 고객 검색 기능 요구사항
사용자는 이름, 전화번호, 가입일자로 고객을 검색할 수 있어야 한다.
검색 결과는 페이지당 20건씩 표시한다.
```
(소스 타입: 파일 / 충돌 정책: llm_merge)

* 기대 출력

```yaml
---
title: "고객 검색"
slug: "고객-검색"
type: "deliverable"
sdlc_phase: "requirements"
domain: "고객 관리"
subdomain: "고객 검색"
status: "active"
source_count: 1
---
```
본문: 정규화된 마크다운 + 지식 그래프 상호참조 엣지, `wiki/index.md`·`log.md` 갱신, 벡터 3개 저장

* 성공 기준

  * 기준 1: 문서가 올바른 SDLC 단계/도메인 폴더 경로에 페이지로 생성된다

  * 기준 2: 13개 노드가 모두 "완료" 상태로 끝나고, 생성 페이지가 위키 뷰어·검색에서 즉시 조회된다

**시나리오 2 : 중복·충돌 문서 적재 → LLM 자동 병합**

* ID : SC-002

* 상황 : 이미 위키에 존재하는 주제의 후속/수정 문서(v2, 보강본)를 추가로 적재할 때

* 목표 : 신규 문서와 기존 페이지의 의미 관계를 판정하여 중복은 통합하고 충돌은 정책에 따라 병합한다

* 사전 조건 : 동일 서브도메인에 유사 페이지가 이미 존재(SC-001 등으로 적재됨), 충돌 정책 선택 가능

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| -- | ------ | ------ | -- |
| 1 | 기존 주제의 개정 문서를 선택하고 충돌 정책 선택 후 적재 시작 | 파이프라인 실행, similarity 노드에서 벡터 검색으로 유사 후보 탐색 | distance 임계값 기반 |
| 2 | similarity 노드 상세에서 병합 대상 페이지 확인 | LLM이 중복/유사 판정 → `{action:"merge", target_slug}` 결정 | 신규 생성 vs 병합 분기 |
| 3 | conflict·merge 노드 진행 확인 | LLM이 의미 관계(모순/보강/중복) 판정 후 본문 병합, merge 레코드 생성 | 충돌 목록 기록 |
| 4 | verify 노드에서 커버리지 확인 | 기존+신규 내용 보존 여부 검증, 누락 시 merge로 1회 루프백 | coverage % 표시 |

* 입력 예시

```markdown
# 고객 검색 기능 요구사항 v2
(기존) 이름, 전화번호, 가입일자 검색 +
(추가) 등급별 필터, CSV 내보내기 옵션 지원
```
(충돌 정책: llm_merge)

* 기대 출력

병합된 단일 페이지(`고객-검색`)에 추가 필터·내보내기 항목 반영, `source_count: 2`, 충돌 리포트 `{relation:"augmentation", conflicts:["필터 옵션 추가"]}`, `/api/merges`에 merge_id 1건 등록

* 성공 기준

  * 기준 1: 신규 페이지가 중복 생성되지 않고 기존 페이지에 통합된다

  * 기준 2: 충돌 정책(llm_merge/manual/prefer_incoming/prefer_existing)에 맞게 처리되고, verify 커버리지가 기존·신규 내용을 모두 보존한다

**시나리오 3 : 위키 검색 및 질의응답**

* ID : SC-003

* 상황 : 누적된 위키에서 특정 주제를 찾거나 자연어로 질문해 답을 얻고자 할 때

* 목표 : 하이브리드 검색(BM25+벡터)으로 관련 페이지를 찾고, 질의응답으로 근거가 인용된 답변을 얻는다

* 사전 조건 : 위키에 페이지가 1건 이상 적재·인덱싱되어 있음

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| -- | ------ | ------ | -- |
| 1 | `위키 뷰어·검색` 화면에서 검색어 입력(필요 시 SDLC 단계 필터) | `GET /search?q=...&phase=...` 하이브리드 검색(RRF 융합) | BM25+벡터 |
| 2 | 검색 결과의 스니펫·단계 배지 확인 후 페이지 진입 | 관련도순 결과 반환, 페이지 본문 표시 | 트리 탐색 병행 |
| 3 | 질의 모드로 전환해 자연어 질문 입력 | `POST /query`로 LLM이 페이지 근거를 인용한 답변 합성 | 출처 인용 포함 |

* 입력 예시

검색어: `고객 검색 필터` / 질의: "고객 검색에서 지원하는 필터 조건은?"

* 기대 출력

검색: 관련 페이지 목록(스니펫·단계 배지). 질의: "이름, 전화번호, 가입일자, 등급별 필터를 지원합니다 [[고객-검색]]" 형태의 인용 포함 답변

* 성공 기준

  * 기준 1: 의도한 페이지가 상위 결과로 노출된다

  * 기준 2: 질의 답변에 근거 페이지(wikilink) 인용이 포함된다

**시나리오 4 : 멀티 에이전트 워크플로우 실시간 시각화**

* ID : SC-004

* 상황 : LLM 기반 위키 자동화 과정을 학습·시연 목적으로 단계별로 관찰하고자 할 때

* 목표 : 적재 파이프라인의 13개 노드 진행과 각 노드의 입출력·판정 근거를 실시간으로 시각적으로 확인한다

* 사전 조건 : 진행 중이거나 완료된 run이 존재(적재 직후 자동 진입)

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| -- | ------ | ------ | -- |
| 1 | 워크플로우 뷰 진입 | SSE 구독, `run_started` 이후 노드별 `node_update` 이벤트 수신 | 직렬 진행 |
| 2 | 노드 상태/소요시간 모니터링 | 각 노드 상태 배지·output_summary·duration 갱신 | 완료 노드 녹색 |
| 3 | decompose가 분기되면 병렬 브랜치 확인, 노드 클릭으로 상세 패널 열람 | 도메인 분해 시 자식 run 생성, 노드별 입력/출력·충돌·커버리지 표시 | 병렬 브랜치 |

* 입력 예시

복합 문서(로그인 명세 + 결제 설계가 한 파일에 혼재) 적재

* 기대 출력

decompose 노드에서 도메인 단위로 분해되어 병렬 자식 run 생성, 각 단계 노드가 순차적으로 완료 상태로 전환, 최종 `run_completed{page_slug, merge_id, spawned_runs}` 수신

* 성공 기준

  * 기준 1: 13개 노드의 상태 전이가 실시간(SSE)으로 지연 없이 반영된다

  * 기준 2: 각 노드의 입력/출력과 LLM 판정 근거를 상세 패널에서 확인할 수 있다

**시나리오 5 : 병합 결과 검토 및 되돌림(diff/revert)**

* ID : SC-005

* 상황 : 자동 병합 결과가 의도와 다를 때 변경 내용을 검토하고 일부 또는 전체를 되돌리고자 할 때

* 목표 : 병합 전/후 diff를 비교하고 라인 단위 또는 병합 전체를 되돌리거나 직접 편집한다

* 사전 조건 : 병합(merge) 레코드가 1건 이상 존재(SC-002 등으로 생성됨)

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| -- | ------ | ------ | -- |
| 1 | `충돌/diff` 화면에서 병합 목록(대상 페이지·충돌 수·커버리지) 확인 | `GET /api/merges` 목록 반환 | 메타데이터 표시 |
| 2 | 특정 병합 선택해 side-by-side diff 열람 | `GET /api/merges/{mid}/diff`로 before↔현재 상태, 라인 단위 hunk 표시 | 라인 단위 |
| 3 | 특정 hunk/전체 되돌림 또는 본문 직접 편집 후 저장 | `POST /api/merges/{mid}/revert`로 원복·재임베딩, 또는 `PUT /api/wiki/pages/{slug}` 저장 | 재임베딩 수행 |

* 입력 예시

병합 ID `a3f2c1e9` 선택 → 추가된 "CSV 내보내기" 라인 hunk 되돌림

* 기대 출력

해당 hunk가 병합 이전 상태로 복원되고 페이지 재임베딩, 변경 이력이 `log.md`에 반영

* 성공 기준

  * 기준 1: 병합 전/후 차이가 라인 단위로 정확히 표시된다

  * 기준 2: 되돌림 후 페이지 본문과 벡터 인덱스가 원래 상태와 일치한다

**시나리오 6 : 지식 그래프 탐색**

* ID : SC-006

* 상황 : 페이지 간 의미 관계(구현·검증·구체화 등)를 한눈에 파악하고자 할 때

* 목표 : 도메인 스윔레인과 타입별 엣지로 위키 페이지 간 연결 관계를 탐색한다

* 사전 조건 : crossref 노드로 생성된 엣지(`wiki/graph/edges.jsonl`)가 존재

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| -- | ------ | ------ | -- |
| 1 | `지식 그래프` 화면 진입 | `GET /api/wiki/graph`로 노드·엣지 로드, 도메인 스윔레인 렌더 | 접이식 레인 |
| 2 | 엣지 타입/신뢰도 배지 확인 | 참조/연관/구현/검증/구체화/중복/병합출처/대체/충돌 9종 + high/medium/low 표시 | 9종 엣지 |
| 3 | 노드 클릭으로 연결 페이지 이동 | 해당 위키 페이지로 이동 | wikilink 연계 |

* 입력 예시

"로그인" 요구사항 페이지 노드 클릭

* 기대 출력

로그인 요구사항 → 로그인 설계(`implements`) → 로그인 테스트(`verifies`)로 이어지는 엣지와 신뢰도 배지 표시

* 성공 기준

  * 기준 1: crossref로 생성된 엣지가 타입·신뢰도와 함께 정확히 시각화된다

  * 기준 2: 엣지를 따라 연결된 페이지로 이동할 수 있다
