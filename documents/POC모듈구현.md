### 핵심 구현 내용

흩어진 개발 문서(요구사항·설계·테스트 등)를 **LLM이 자동으로 한 권의 위키로 정리**해 주는 시스템이다. 문서를 한 건 올리면 여러 AI 에이전트가 순서대로 처리해 페이지를 만들거나 기존 페이지에 합쳐 주고, 그 과정을 화면에서 **실시간 흐름도**로 볼 수 있다.

**1.1 에이전트 워크플로우 (Agent Workflow)**

* **구현 기능:** 문서 1건을 위키 페이지로 만드는 **13개 에이전트 자동 파이프라인**. 각 단계 진행 상태가 흐름도 노드에 실시간 표시된다.

* **동작 원리** (한 줄 요약: *"수집 → 이해 → 비교 → 합치기 → 정리"*):
  1. **수집·파싱·정규화** — 문서에서 제목/본문을 뽑고 SDLC 단계(요구사항/설계/테스트)로 분류.
  2. **도메인 분해** — 여러 주제가 섞여 있으면 주제별로 갈라 병렬 처리.
  3. **청킹·임베딩** — 본문을 작은 조각으로 잘라 벡터 DB에 저장.
  4. **유사도·충돌 판정** — 벡터로 후보를 추리고, **LLM이 정말 같은 내용인지 한 번 더 확인**.
  5. **병합(merge)** — 새 페이지로 만들지 기존과 합칠지 결정해 파일에 쓴다.
  6. **누락 검토(verify)** — 합친 결과에 빠진 게 있으면 **병합으로 1회만 되돌려** 보완.
  7. **상호참조·인덱싱·로깅** — 관련 페이지 링크와 목차/활동 로그 갱신.

* **주요 기술:** LangGraph(분기·반복이 가능한 단계 그래프), OpenAI gpt-4o-mini / Azure OpenAI(JSON 모드 강제), FastAPI + SSE(진행 상황 실시간 스트리밍).

**1.2 도구(Tool) 및 함수 연동**

* **구현 기능:** **충돌 해결 방식 4종을 골라 쓰는 구조** — (a) LLM 자동 병합(기본), (b) 사람이 직접 판단, (c) 새 문서 우선, (d) 기존 문서 우선. + 위키 파일/폴더 자동 정리, 파일·URL 두 입력 방식.

* **동작 원리:** 충돌 처리 방식이 **"전략 4장이 등록된 사전"** 형태라, 설정 한 줄로 동작이 바뀐다. 새 전략 추가 시 파이프라인 본체는 그대로. 페이지 파일은 항상 **머리말(메타데이터) + 본문** 구조라 뒤따르는 검색·인덱싱이 메타에 의존해 동작한다.

* **주요 기술:** Python `TypedDict`로 단계 간 상태 관리, FastAPI 라우터로 API 분리, 외부 의존 없는 작은 `.env` 로더.

**1.3 데이터 및 메모리 (RAG & Context)**

* **구현 기능:** **중복 페이지 자동 감지** + **하이브리드 검색**(단어 + 의미) + **인용 기반 질의응답**(답변에 참조 페이지 링크 포함).

* **동작 원리** (한 줄 요약: *"단어로도, 의미로도 찾고 둘을 섞어 순위"*):
  - 본문을 청크로 자르고 임베딩해 Chroma에 저장.
  - 검색은 **BM25(단어 일치)**와 **벡터(의미 일치)** 두 순위를 RRF로 합쳐 페이지별 점수 계산.
  - **오프라인 폴백** — LLM 키가 없을 때 단어 해시로 만든 가짜 1536차원 벡터를 사용. **차원이 같아 코드 수정 없이** 전체 흐름이 그대로 돈다.

* **주요 기술:** Chroma(코사인 유사도), OpenAI `text-embedding-3-small`(1536차원), `rank_bm25`, Reciprocal Rank Fusion.

### 주요 문제 해결 및 기술 리서치

| 이슈 구분 | 문제 상황 및 원인 | 리서치 및 해결 과정 |
| --- | --- | --- |
| **프롬프트 / LLM 판정** | 벡터 유사도만으로 중복을 판단하니, **단어만 비슷한 다른 문서를 같다고 판정**하는 실수 발생. | • RAG의 "넓게 후보 → 좁게 재검증" 2단계 패턴 적용. **벡터는 후보 추리기, LLM이 최종 판정**으로 분리하고, LLM은 JSON 모드 + 판단 근거를 함께 출력. |
| **도구 연동 / API 키 분리** | OpenAI와 Azure OpenAI를 동시 지원해야 하는데 두 키가 섞이면 엉뚱한 호출 발생. | Azure/OpenAI 키를 **다른 환경변수로 분리**, "Azure → OpenAI → 오프라인" **우선순위 한 줄**로 결정. `/api/health`에서 현재 모드 확인 가능. |
| **에이전트 그래프 / 누락 보완** | LLM이 두 문서를 합칠 때 한쪽 내용을 빠뜨리는 경우가 있어 무한 반복 위험과 데모 안정성 사이 균형 필요. | 병합 후 **누락 검토 단계**가 점검, 빠진 게 있으면 **병합으로 1회만** 되돌리는 **횟수 제한 재시도** 도입. 무한 루프 원천 차단. |
| **데이터 / 오프라인 폴백** | LLM 키 없는 데모 환경에서 단순 mock으로 응답하면 임베딩 차원이 안 맞아 벡터 DB 저장에서 에러. | 키 없을 때 **단어 해시로 1536차원 가짜 벡터** 생성. 모양이 진짜와 같아 시각화·병합·검색·질의응답까지 코드 수정 없이 동작. |
| **프론트엔드 / 시각화 안정성** | SSE로 노드 상태가 빠르게 갱신될 때 React Flow 캔버스에서 **노드/엣지가 사라지고 fit-view로도 복구 안 되는** 현상. | React Flow v11의 controlled 패턴(`useNodesState`/`useEdgesState`) + `ReactFlowProvider`로 전환하고, `ResizeObserver`로 컨테이너 변동 시 자동 fitView. |

### 핵심 동작 검증

**[검증 시나리오: 같은 기능의 v1·v2 명세서가 따로 들어왔을 때, 위키가 자동으로 한 페이지로 합쳐 주는가]**

* **입력 1 — v1 적재:** `01-login-spec.md` (로그인 요구사항 기본안)

  → **수집·파싱·정규화**: "요구사항" 단계로 분류 → **유사도**: 후보 0건, "신규 생성" 결정 → **병합**: 신규 페이지 생성(출처 1) → **누락 검토**: 신규라 불필요 → **인덱싱·로깅**.

* **입력 2 — v2 적재:** `02-login-spec-v2.md` (v1 + 소셜 로그인/세션 30분/잠금 5회 추가)

  → **유사도**: 벡터 검색이 v1을 후보로 찾음 → **LLM 재확인**: "동일 기능의 개정 버전, 기존에 합쳐라" 결정 → **충돌 판정**: "보강/갱신 관계", 모순 0건 → **병합(자동)**: v1+v2를 LLM이 통합본으로 정리해 같은 페이지에 갱신(출처 2) → **누락 검토**: v1·v2의 핵심 조항이 모두 통합본에 있는지 확인, 누락 0건 → **상호참조·로깅**.

* **최종 결과:**

  - 위키에 **딱 1개 페이지**만 존재하고, **v1·v2 모든 핵심 조항을 함께 담은 통합본**(`source_count=2`)이 작성됨.
  - 프론트엔드는 13개 Agent 노드가 순차 점등되며, 오른쪽 상세 패널이 **방금 끝난 단계의 결과**(병합 페이지명, merge_id, 본문 미리보기)를 실시간 표시.
  - "생성된 페이지 보기 →"로 위키 뷰어 이동 시 **왼쪽 폴더 트리가 해당 페이지까지 자동 펼쳐지고 스크롤**.
  - 충돌 정책을 `manual`로 바꾸면 자동 병합 대신 **두 페이지를 그대로 두고 사람이 diff 화면에서 accept/revert**하는 모드로 동작.
