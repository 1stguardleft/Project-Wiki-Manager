# 주문 관리 - 주문 처리 - 설계

**문서 버전:** v2.0  
**도메인 / 서브도메인:** 주문 관리 / 주문 처리  
**SDLC 단계:** 설계  
**변경 요점 (vs 1차):** Order에 employee_id/memo 컬럼, 등록 시 재고 부족 검증, DELETE 시 복원.

## 1. 설계 개요

CRUD 외에 employee FK, memo 컬럼, 재고 부족 거부, 삭제 시 복원이 추가된다. 1차에는 직원·메모 등 부가 컬럼 없음.

## 2. 구성 요소

| 계층       | 구성 요소         | 역할                           |
|------------|------------------|--------------------------------|
| Controller | OrderController   | CRUD                           |
| Service    | OrderService      | 트랜잭션 + 재고/직원 검증      |
| Entity     | Order             | employee_id, memo, 신규 금액 컬럼 |
| Repository | OrderRepository   | derived query                  |

## 3. 데이터 모델 (변경)

| 컬럼                                   | 타입         | 제약                       |
|----------------------------------------|--------------|----------------------------|
| employee_id                            | FK           | NOT NULL (2차 신규)       |
| memo                                   | varchar(200) | nullable (2차 신규)       |
| supply_amount / vat_amount / discount_amount / total_amount | bigint       | NOT NULL (2차 신규/확장) |

## 4. API 인터페이스

| 메서드 | 경로               | 설명                             |
|--------|-------------------|----------------------------------|
| POST   | /api/orders       | 등록 (재고 부족 거부, 직원 필수) |
| GET    | /api/orders       | 전체                             |
| GET    | /api/orders/{id}  | 상세                             |
| DELETE | /api/orders/{id}  | 삭제 + 재고 복원                |

## 5. 처리 흐름

- 등록: customer/product/employee 존재 → 재고 검증 → 금액 계산 → save → 201
- 삭제: 존재 확인 → 재고 복원 (status 무관) → delete → 204

## 6. 설계 규칙

- 등록은 `@Transactional`, 재고 락(비관적/낙관적) 검토 후 적용.
- DELETE 시 항상 복원 (1차와 차이). 1차에는 DELETE 시 재고 복원하지 않음.
- 응답 표준 [[공통API응답]].
