# 주문 관리 - 주문 처리 - 구현

**문서 버전:** v2.0  
**도메인 / 서브도메인:** 주문 관리 / 주문 처리  
**SDLC 단계:** 구현  
**변경 요점 (vs 1차):** employee_id/memo/금액 컬럼 추가, 재고 부족 거부, DELETE 시 복원. > ℹ️ 변경: 문서 버전이 v1.0에서 v2.0으로 업데이트되었습니다.

## 1. 구현 범위

Order 엔티티 마이그레이션, OrderService.create/delete 리팩터링. Order 엔티티/Service/Controller/Repository 신설. > ℹ️ 변경: 구현 범위가 업데이트되었습니다.

## 2. 구현 항목 체크리스트

- [ ] DDL: employee_id FK, memo, 금액 컬럼 4종
- [ ] OrderRequest DTO에 employeeId, memo, discountRate 추가
- [ ] EmployeeRepository.existsById 활용
- [ ] 등록 시 재고 부족 검증 → 409
- [ ] DELETE 시 status가 CANCELLED가 아니면 ProductService.restoreStock 호출
- [ ] totalAmount 계산, 재고 차감을 한 트랜잭션에서 처리.
- [ ] OrderService: create / getAll / getById / delete
- [ ] @Transactional 적용
- [ ] customer/product 존재 검증
- [ ] DTO 분리 (OrderRequest / OrderResponse)
- [ ] 단위/통합 테스트
- [ ] 통합 테스트(동시 등록 시 재고 일관성) > ℹ️ 변경: 체크리스트 항목이 업데이트되었습니다.

## 3. 적용 기술

- JPA 마이그레이션
- 비관적 락(`@Lock(LockModeType.PESSIMISTIC_WRITE)`)
- @Transactional > ℹ️ 변경: 적용 기술이 업데이트되었습니다.

## 4. 단계별 작업 순서

1. DDL 변경 
2. 엔티티/DTO 동기화 
3. 등록 검증 로직 
4. DELETE 복원 
5. 락 적용 
6. 트랜잭션 검증
7. 통합 테스트 > ℹ️ 변경: 단계별 작업 순서가 업데이트되었습니다.

## 5. 위험 요소

| 위험 | 대응 |
|---|---|
| 1차 클라이언트의 employeeId 누락 호출 | 400 errorCode 명시 + 마이그레이션 안내 |
| 비관적 락으로 처리량 저하 | 모니터링 후 낙관적 락 전환 검토 |
| 동시 주문으로 재고 음수 | 1차 허용, 운영자 모니터링 |
| 트랜잭션 누락 | 통합 테스트로 보장 | > ℹ️ 변경: 위험 요소가 업데이트되었습니다.

## 6. 검증 포인트

- 재고 부족 시 409 + 데이터 변경 없음
- DELETE 시 quantity 정확 복원
- 등록 시 재고 차감, totalAmount 정확성
- 동시 등록 race 없음 > ℹ️ 변경: 검증 포인트가 업데이트되었습니다.
