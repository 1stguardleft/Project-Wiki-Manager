# 상품 관리 - 재고 관리 - 요구사항

**문서 버전:** v2.0  
**도메인 / 서브도메인:** 상품 관리 / 재고 관리  
**SDLC 단계:** 요구사항  
**변경 요점 (vs 1차):** StockHistory 이력 테이블 도입, 운영자 재고 조정 API 정식 노출, 임계값 파라미터화, 음수 재고 차단.

## 1. 개요

재고 변동의 추적성을 확보하기 위해 모든 재고 변경을 이력 테이블에 적재하고, 운영자가 직접 재고를 조정할 수 있는 별도 API를 제공한다. 재고 부족 임계값은 **10으로 고정**(파라미터 미제공).

## 2. 사용자 시나리오

- 재고 담당자가 실측 결과 차이가 난 상품의 재고를 직접 조정한다(`PATCH /api/products/{id}/stock`).
- 매니저가 재고 변동 이력을 조회해 손실 추적 자료로 활용한다.
- 운영자가 `?threshold=20`으로 "20개 미만" 상품을 조회한다.

## 3. 기능 요구사항

| ID | 요구사항 | 설명 | 우선순위 |
|---|---|---|---|
| 재고-01 | 재고 부족 조회 | quantity < threshold (기본 10) | 필수 |
| 재고-02 | 재고 조정 | 운영자가 직접 재고를 갱신 | 필수 |
| 재고-03 | 재고 변동 이력 적재 | 모든 변동(주문/취소/조정)을 StockHistory에 기록 | 필수 |
| 재고-04 | 재고 변동 이력 조회 | 특정 상품의 변동 이력 조회 (신규) | 권장 |

## 4. 관리 정보 (StockHistory)

| 항목 | 형식 | 설명 |
|---|---|---|
| product_id | FK | 상품 |
| delta | 정수 | 변동량(+/-) |
| reason | enum | ORDER / CANCEL / ADJUST |
| memo | 문자열 | 운영자 조정 시 메모 |
| createdAt | timestamp | 발생 시각 |

## 5. 업무 규칙

- 재고 변경 후 quantity가 음수가 되면 **거부**(주문 시 재고 부족 오류).
- 운영자 조정 시 memo 필수, reason은 ADJUST 고정.
- threshold 범위 1~1000.
- 재고 변경 이력은 별도 보존하지 않음.
- 운영자가 임의로 재고를 조정하는 별도 기능은 1차 범위 아님.

## 6. 비기능 요구사항

- 이력 적재로 인한 추가 지연 100ms 이내.
- 재고 조정 동시 호출 시 데이터 일관성 보장.
- 재고 부족 조회 응답 1초 이내.

## 7. 예외 처리

| 상황 | 처리 |
|---|---|
| 재고 음수 발생 | 409, errorCode = INSUFFICIENT_STOCK |
| 조정 시 memo 누락 | 400 |
| threshold 범위 초과 | 1 또는 1000으로 클램프 |
