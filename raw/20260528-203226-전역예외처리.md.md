# 공통/인프라 - 전역 예외 처리 - 설계 (2차)

**문서 버전:** v2.0 (2차)
**도메인 / 서브도메인:** 공통/인프라 / 전역 예외 처리
**SDLC 단계:** 설계
**변경 요점 (vs 1차):** 핸들러 4종 분리, errorCode enum 도입, 도메인 예외 매핑 표준화.

## 1. 설계 개요

`@ControllerAdvice`에 4종 핸들러를 두고 도메인 커스텀 예외(`BusinessException`)를 errorCode와 함께 잡는다.

## 2. 구성 요소

| 계층 | 구성 요소 | 역할 |
|---|---|---|
| Advice | GlobalExceptionHandler | 예외 핸들러 |
| Exception | BusinessException(errorCode, message) | 도메인 커스텀 예외 |
| Enum | ErrorCode | errorCode 상수 카탈로그 |

## 3. 핸들러 매핑

| 예외 타입 | HTTP | errorCode |
|---|---|---|
| MethodArgumentNotValidException / ConstraintViolationException | 400 | VALIDATION_FAILED |
| HttpMessageNotReadableException | 400 | INVALID_REQUEST |
| EntityNotFoundException | 404 | NOT_FOUND |
| DataIntegrityViolationException | 409 | (UNIQUE 위반 → DUPLICATE_*) |
| BusinessException | 4xx (예외에 정의된 코드) | 예외 errorCode |
| 그 외 Exception | 500 | UNKNOWN_ERROR |

## 4. 처리 흐름

1. 예외 발생 → @ExceptionHandler 호출
2. ErrorCode 결정 → message 매핑 (ErrorCode → 한글 메시지 표)
3. ApiResponse.fail(code, message) 반환
4. ERROR 레벨 로그 (errorCode 포함)

## 5. 설계 규칙

- DataIntegrityViolation은 메시지 분석으로 DUPLICATE_* 식별 (제약명 기반).
- BusinessException은 도메인 Service에서 명시적으로 throw.
- stacktrace 미노출.
