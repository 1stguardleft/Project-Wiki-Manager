# 고객 관리 - 고객 변경 이력 - 설계 (2차)

**문서 버전:** v2.0 (2차)
**도메인 / 서브도메인:** 고객 관리 / 고객 변경 이력
**SDLC 단계:** 설계
**변경 요점 (vs 1차):** CustomerHistory 엔티티/Repository 신설, Service에 변경 감지 + 이력 적재 로직.

## 1. 설계 개요

수정 흐름에서 **변경된 필드만 골라 이력 row를 적재**한다. 트랜잭션 일관성 유지.

## 2. 구성 요소

| 계층 | 구성 요소 | 역할 |
|---|---|---|
| Service | CustomerService | 변경 감지 + 이력 적재 |
| Entity | CustomerHistory | 변경 이력 row (신규) |
| Repository | CustomerHistoryRepository | 이력 조회 |
| Controller | CustomerController | 이력 조회 API |

## 3. 데이터 모델 (신규 CustomerHistory)

| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | bigint | PK |
| customer_id | FK | NOT NULL |
| field | varchar(40) | NOT NULL |
| old_value | varchar(255) | nullable |
| new_value | varchar(255) | nullable |
| changed_at | timestamp | 자동 |
| changed_by | varchar(80) | 운영자 ID (시스템 기본값) |

인덱스: `(customer_id, changed_at)`

## 4. API 인터페이스

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | /api/customers/{id}/history | 고객별 변경 이력 |

## 5. 처리 흐름

- 수정 메서드: before(Customer 스냅샷) → save → field별 비교 → 변경된 필드만 CustomerHistory insert (같은 트랜잭션)

## 6. 설계 규칙

- 변경 없는 필드는 row 미생성.
- 트랜잭션 안에서 처리 (예외 시 모두 롤백).
- 보존 기간 5년(추후 정책 정의).
