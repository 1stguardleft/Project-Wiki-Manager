# 프로젝트 테일러링 가이드

## 문서 목적

이 문서는 표준 개발 프로세스를 현재 프로젝트 상황에 맞게 조정하기 위한 기준을 정의한다.
프로젝트 규모, 팀 구성, 일정 제약, 외부 의존성을 고려하여 어떤 활동을 유지하고 어떤 활동을 축소하거나 생략할지 합의하는 데 목적이 있다.

## 적용 범위

- 신규 웹 서비스 개발 프로젝트
- 3개월 이내의 단기 구축 과제
- 내부 개발자 4명 이하의 소규모 팀
- 외부 솔루션 연동이 포함된 프로젝트

## 테일러링 원칙

### 1. 필수 활동 유지

다음 활동은 프로젝트 규모와 관계없이 유지한다.

- 요구사항 정의 및 승인
- 아키텍처 검토
- 개발 산출물 형상관리
- 테스트 결과 기록
- 배포 전 체크리스트 확인

### 2. 경량화 대상

다음 활동은 프로젝트 상황에 따라 축소할 수 있다.

- 상세 설계 문서 분량
- 주간 보고 형식
- 테스트 케이스 문서 수준
- 회의 빈도와 참석 범위

### 3. 생략 금지 항목

아래 항목은 일정이 촉박하더라도 생략하지 않는다.

- 개인정보 또는 인증 관련 보안 검토
- 운영 이관 문서
- 장애 대응 연락 체계
- 요구사항 변경 이력 관리

## 프로젝트 특성별 조정 기준

## 일정이 매우 짧은 경우

- 상세 설계는 핵심 화면, API, 데이터 모델 중심으로만 작성한다.
- 비핵심 화면은 와이어프레임 대신 간단한 메모로 대체할 수 있다.
- 일일 스탠드업은 15분 이내로 제한한다.
- 주간 보고는 문서 대신 작업 보드 스냅샷으로 대체할 수 있다.

## 외부 연동 비중이 높은 경우

- 인터페이스 명세는 별도 관리한다.
- 연동 실패 시 재처리 정책을 반드시 정의한다.
- 테스트 단계에서 Mock 환경과 실제 환경 검증을 구분한다.
- 외부 시스템 담당자 연락처와 대응 SLA를 운영 문서에 포함한다.

## 팀 규모가 작은 경우

- 역할은 PM, 개발, 테스트를 완전히 분리하지 않고 겸임 가능하다.
- 코드 리뷰는 1인 승인으로 진행할 수 있다.
- 품질 점검은 체크리스트 기반으로 수행한다.
- 회의록은 모든 회차에 작성하지 않고 의사결정이 있는 경우만 남긴다.

## 산출물 테일러링 표

| 산출물 | 기본 정책 | 축소 가능 조건 | 생략 가능 여부 |
|------|------|------|------|
| 프로젝트 계획서 | 작성 | 소규모 프로젝트는 간략 버전 허용 | 불가 |
| 요구사항 정의서 | 작성 | 사용자 스토리 기반 간략화 가능 | 불가 |
| 상세 설계서 | 작성 | 핵심 기능 중심으로 축소 가능 | 조건부 가능 |
| 테스트 케이스 | 작성 | 핵심 시나리오 우선 작성 | 조건부 가능 |
| 운영 이관 문서 | 작성 | 분량 축소 가능 | 불가 |
| 주간 보고서 | 작성 | 보드 캡처 또는 요약 메모 대체 가능 | 가능 |

## 역할별 책임

### PM

- 테일러링 범위 승인
- 요구사항 변경 관리
- 대외 커뮤니케이션 총괄

### 아키텍트 또는 리드 개발자

- 설계 산출물 최소 기준 정의
- 공통 컴포넌트 및 기술 표준 결정
- 품질 리스크 검토

### 개발자

- 구현 산출물 작성
- 코드 리뷰 수행
- 테스트 결과 기록

### QA 또는 테스트 담당

- 핵심 시나리오 검증
- 결함 추적
- 배포 전 점검 결과 정리

## 운영 전환 기준

운영 전환 전에는 아래 항목을 모두 확인한다.

- 배포 절차 문서 최신화
- 장애 대응 연락망 공유
- 운영 계정 및 권한 확인
- 로그 확인 방법 문서화
- 백업 및 복구 절차 확인

## 변경 관리

프로젝트 진행 중 다음 상황이 발생하면 테일러링 기준을 다시 검토한다.

- 일정 20% 이상 변동
- 외부 연동 시스템 추가
- 인력 구성 변경
- 보안 요구사항 추가
- 운영 범위 확대

## 승인 기록

- 초안 작성: PM
- 기술 검토: 리드 개발자
- 최종 승인: 프로젝트 책임자
