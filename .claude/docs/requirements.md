# Project Wiki Manager — 요구사항 정의서 (1차)

> 본 문서는 [problem-definition.md](./problem-definition.md)의 문제 정의와
> [references/llm-wiki.md](./references/llm-wiki.md)의 기술 패턴(LLM Wiki)을 바탕으로
> 작성한 1차 요구사항이며, 사용자 확정 답변(§10)을 반영했다. 세부 사항은 구현을 진행하며 보완한다.
> 구현 시 재사용 가능한 참조 구현 분석은 [omegawiki-reuse.md](./omegawiki-reuse.md) 참고.

## 1. 개요

### 1.1 목적
**소규모 개발 프로젝트(개발자 최대 10명)** 에서 흩어져 있고 중복되는 산출물 문서를,
LLM이 **지속적으로 구축·유지하는 위키**로 통합하여 탐색 시간과 관리 공수를 줄이고
문서 일관성을 확보한다. 위키는 개발 산출물을 **개발 Lifecycle(Waterfall) 단계**에
맞춰 분류·관리한다.

> **프로젝트 성격(중요)**: 본 과제는 **회사 내부 교육 실습 프로젝트**다. 완성도 높은
> 구현뿐 아니라 **UI를 통한 시각화가 매우 중요**하며, 특히 핵심 작업이 **멀티 에이전트
> (오케스트레이터 + 전문 에이전트) 워크플로우로 처리되는 과정**을 시각적으로 보여 주는 것이
> 핵심 목표다. 향후 이 결과물로 **발표 자료**를 작성한다. 또한 과제 요건상 **VectorDB 사용이
> 필수**다.

### 1.2 핵심 컨셉
질의 시점에만 원문을 검색(RAG)하는 방식이 아니라, **출처가 들어올 때마다 LLM이
위키를 점진적으로 갱신·축적**한다. 위키는 사용자와 원문 사이에 위치한, 구조화되고
상호 링크된 마크다운 파일의 집합이며 누적·지속되는 산출물이다.

### 1.3 핵심 원칙
- **원본 불변**: 원본 출처(raw source)는 진실의 원천이며 LLM은 읽기만 한다.
- **위키 소유권**: 위키 본문은 LLM이 작성·유지한다. 사람은 출처 큐레이션·탐색·질문에 집중한다.
- **누적성**: 상호 참조·충돌 표시·종합 결과는 한 번 만들어진 뒤 계속 최신 상태로 유지된다.
- **SDLC 정렬**: 위키 페이지·디렉토리는 표준 Waterfall 단계(요구사항→설계→구현→테스트→배포→운영)를 기준으로 분류한다.
- **시각화 우선**: 멀티 에이전트 워크플로우의 진행 과정을 실시간으로 관찰·시연할 수 있어야 한다(교육·발표 목적).
- **VectorDB 활용**: 임베딩 기반 VectorDB를 검색·유사도·내용 보강의 공통 기반으로 사용한다(과제 필수 요건).

## 2. 용어 정의

| 용어 | 정의 |
| --- | --- |
| 원본 출처(Raw Source) | 사용자가 수집한 원본 문서(웹페이지·로컬 md 파일). 불변 계층. 본 프로젝트에서는 **로컬 md 파일을 Confluence 대체 소스로 간주**한다. |
| 위키(Wiki) | LLM이 생성·유지하는 마크다운 파일 디렉토리. SDLC 단계별 산출물 페이지 + 엔티티·개념·종합 페이지. |
| 스키마(Schema) | 위키 구성·규약·워크플로를 LLM에게 지시하는 설정 문서(`CLAUDE.md`/`AGENTS.md`). |
| 적재(Ingest) | 새 출처를 읽고 위키에 통합하는 작업. |
| 질의(Query) | 위키를 대상으로 질문하고 인용 기반 답을 종합하는 작업. |
| 린트(Lint) | 위키의 정합성·건강 상태를 점검·교정하는 작업. |
| 정규화(Normalize) | 원문을 제목/본문/리스트 등 의미 단위로 재구성하고 불필요 요소를 제거하는 작업. |

## 4. 시스템 아키텍처 (3계층)

```
[웹 앱]  React 프론트엔드  ──HTTP/SSE──▶  Python 백엔드(API + LLM 오케스트레이션)
                                                │  읽기/쓰기
                                                ▼
[원본 출처 계층]  raw/        ← 불변. 수집된 원문(웹페이지 HTML→MD, 로컬 md 파일)
       │  ingest
       ▼
[위키 계층]       wiki/       ← LLM 소유. SDLC 단계별 산출물 페이지 + index.md + log.md
       │  query / lint            └ 검색: 하이브리드(BM25+벡터) 인덱스
       ▼
[스키마 계층]     CLAUDE.md   ← 위키 규약·워크플로 정의(LLM을 위키 관리자로 동작시킴)
```

- **웹 앱 계층**: Python 백엔드 + React 프론트엔드. 적재·질의·린트를 사용자가 웹 UI로 수행하며, **멀티 에이전트 워크플로우 진행 과정을 실시간 시각화**한다.
- **원본 출처 계층**: 수집된 원문을 보관. LLM은 읽기 전용.
- **위키 계층**: 생성된 마크다운 페이지 + 카탈로그(`index.md`) + 타임라인(`log.md`) + 검색 인덱스.
- **스키마 계층**: 위키 구조·규약·워크플로를 기술하는 설정 파일. 사용자·LLM이 함께 진화시킴.

### 4.1 멀티 에이전트 구성 (LangGraph, 세분화 노드)
핵심 작업(적재)은 **오케스트레이터 + 세분화된 전문 노드**의 LangGraph 상태머신으로 처리하며,
각 노드의 진행 상황을 프론트엔드로 스트리밍하여 노드 그래프로 시각화한다. 시각화가 과제 핵심이므로
단계를 세분화하여 진행 과정을 풍부하게 드러낸다.

```
              ┌──────────────────────────────┐
 사용자 요청 ─▶│   Orchestrator (LangGraph)    │ ← 라우팅·상태 집계·이벤트 발행
              └──────────────┬───────────────┘
   ┌──────┬──────┬──────┬────┴────┬──────┬──────┬───────┬──────┬──────┐
   ▼      ▼      ▼      ▼         ▼      ▼      ▼       ▼      ▼      ▼
 fetch  parse normalize chunk    embed similarity merge crossref index  log
 (수집) (파싱) (정규화) (청킹)  (임베딩)(유사도) (병합)(상호참조)(인덱싱)(로깅)
   └──────────── 노드별 이벤트(상태·입출력·소요시간) SSE 스트리밍 ──────────┘
                                  │
                                  ▼               (별도 on-demand) lint (린트)
                       React Flow 워크플로우 뷰
```

#### 노드(전문 에이전트) 책임 계약
| 노드 | 책임 | 입력 | 출력 | 관련 FR |
| --- | --- | --- | --- | --- |
| **fetch** | URL/파일 수집 → `raw/` 저장 | URL 또는 업로드 파일 | 원문(raw 경로) | FR-ING |
| **parse** | HTML 등 포맷 파싱 → 텍스트 | 원문 | 평문/구조 텍스트 | FR-ING-3 |
| **normalize** | 구조 재구성·불필요 요소 제거 | 파싱 텍스트 | 정규화 md | FR-NORM-1·2 |
| **chunk** | 의미 단위 분해 | 정규화 md | 청크 목록 | FR-NORM-3 |
| **embed** | 청크 임베딩 → Chroma 저장 | 청크 목록 | 벡터 ID 목록 | FR-VDB-1·3 |
| **similarity** | 벡터 후보 검색 + LLM 유사/중복 판정 | 청크/문서 | 유사 페이지 후보·판정 | FR-SIM |
| **merge** | 자동 통합 or 신규 페이지 생성, 충돌 표시 | 판정 결과 | 위키 페이지(변경/생성) | FR-MERGE, FR-OUT-1 |
| **crossref** | 위키링크·그래프 엣지 갱신 | 변경 페이지 | 갱신된 링크/엣지 | FR-MERGE-3 |
| **index** | `index.md` + 검색 인덱스 갱신 | 변경 페이지 | 갱신된 인덱스 | FR-IDX, FR-SRCH-3 |
| **log** | `log.md` append | 실행 요약 | 로그 항목 | FR-LOG |
| **lint** (on-demand) | 위키 건강 점검 | 위키 전체 | 점검 리포트 | FR-OPS-3 |

- **Orchestrator**: 요청을 노드 경로로 라우팅하고 상태머신 전이를 관리, 노드별 이벤트를 발행·집계.
- **조건 분기**: similarity 결과에 따라 merge(통합) vs 신규 생성으로 분기.

### 4.2 워크플로우 이벤트 스키마 (시각화 계약)
백엔드는 적재 실행(run)마다 SSE 채널로 노드 단위 이벤트를 발행한다. 프론트(React Flow)는
`node_id`를 그래프 노드에 매핑하고 `status`로 색·아이콘을 갱신한다.

- **run 레벨 이벤트**: `run_started`, `run_completed`, `run_failed` — `{ run_id, source, started_at, ended_at, summary }`
- **node 레벨 이벤트**: `node_update`
  ```json
  {
    "run_id": "string",
    "node_id": "embed",
    "node_label": "임베딩",
    "status": "queued|running|succeeded|failed|skipped|awaiting_input",
    "started_at": "ISO8601",
    "ended_at": "ISO8601|null",
    "duration_ms": 0,
    "input_summary": "청크 12개",
    "output_summary": "벡터 12개 저장(collection=wiki)",
    "artifacts": [{ "type": "page|chunk|edge|vector", "ref": "string" }],
    "message": "string|null",
    "error": "string|null"
  }
  ```
- **전송**: SSE(`text/event-stream`), run별 1채널. (양방향 제어 필요 시 WebSocket로 승격 가능)

### 4.3 휴먼인더루프 & 에러 처리
- **HITL**: 단건 인터랙티브 적재(Q13)이므로 사용자가 각 노드 진행·결과를 확인한다. 병합은 자동
  수행하되(Q14) merge 노드가 충돌·변경 지점을 표시하고, 선택적으로 commit 직전 `awaiting_input`
  상태로 일시정지하여 사용자 승인을 받을 수 있다.
- **에러/재시도**: 외부 호출 노드(fetch·embed·LLM)는 N회 재시도 후 실패 시 `failed` 이벤트 발행.
  실패 노드 이후 단계는 `skipped` 처리하고 run은 부분 실패로 종료(이미 저장된 raw·청크는 보존).
- **재실행**: 실패 지점부터 재개(resume) 가능하도록 run 상태를 보존한다.

## 5. 기능 요구사항 (FR)

### 5.1 수집 (Ingestion)
- **FR-ING-1** 사용자가 입력한 **단건 URL**로부터 웹페이지를 수집·md로 변환한다. (크롤링 미지원)
- **FR-ING-2** **로컬 md 파일을 Confluence 대체 소스로 간주**하여 수집한다. (이번 개발 범위에서 Confluence 직접 연동은 제외)
- **FR-ING-3** HTML·Markdown 등 다양한 포맷을 입력으로 처리한다.
- **FR-ING-4** 로컬 마크다운/파일 업로드(웹 UI)를 지원한다.
- **FR-ING-5** 수집한 원문은 원본 계층(`raw/`)에 불변 형태로 저장한다.

### 5.2 정규화 (Normalization)
- **FR-NORM-1** 문서 구조(제목·본문·리스트 등)를 재구성한다.
- **FR-NORM-2** 광고·내비게이션 등 불필요 요소를 제거한다.
- **FR-NORM-3** 문서를 의미 단위로 분해(Chunking)한다.

### 5.3 유사도 분석 (Similarity Detection)
- **FR-SIM-1** 문서 간 의미 기반 유사도를 **LLM 판단**으로 평가한다. (임베딩 점수 단독 판정이 아닌 LLM 판단을 1차 기준으로 사용; 벡터 검색은 후보 추리기에 활용 가능)
- **FR-SIM-2** 중복·유사 문서를 그룹화한다.
- **FR-SIM-3** 신규 출처가 기존 위키 주장과 충돌하는 부분을 탐지·표시한다.

### 5.4 통합 (Merge)
- **FR-MERGE-1** 유사 문서를 하나의 위키 페이지로 **자동 통합**한다.
- **FR-MERGE-2** 충돌·변경 지점을 **명확히 표시**하고 상충 시 출처를 명시하여, 사용자가 사후 검토할 수 있게 한다. (자동 병합 + 표시 방식)
- **FR-MERGE-3** 통합 시 관련 엔티티·개념 페이지의 상호 참조를 갱신한다.

### 5.5 출력 생성 (Output Generation)
- **FR-OUT-1** 정제된 문서를 Markdown 페이지로 생성한다.
- **FR-OUT-2** (선택) 비교 표·슬라이드(Marp)·차트 등 질의 목적에 맞는 형태로 출력한다.
- **FR-OUT-3** 가치 있는 질의 결과는 새 위키 페이지로 다시 정리해 누적한다.

### 5.6 인덱싱·로깅
- **FR-IDX-1** `index.md`에 전체 페이지 카탈로그(링크·한 줄 요약·카테고리·메타데이터)를 유지하고 적재 시마다 갱신한다.
- **FR-LOG-1** `log.md`에 적재/질의/린트 이벤트를 append-only로 기록한다.
- **FR-LOG-2** 로그 항목은 파싱 가능한 일관 접두사를 사용한다. 예: `## [2026-04-02] ingest | Article Title`.

### 5.7 위키 운영 워크플로
- **FR-OPS-1 (Ingest)** 출처 읽기 → 핵심 시사점 정리 → 위키 페이지 작성/갱신 → 인덱스 갱신 → 로그 기록의 흐름을 수행한다. **단건 인터랙티브 적재**를 기본으로 하며, 사용자가 단계별 진행·결과를 확인한다.
- **FR-OPS-2 (Query)** 관련 페이지를 찾아 읽고 **인용을 달아** 답을 종합한다.
- **FR-OPS-3 (Lint)** 위키 건강 점검을 수행한다: 페이지 간 모순, 무효화된 오래된 주장, 고아 페이지, 누락된 개념/상호 참조, 데이터 공백 탐지 및 보완 제안.

### 5.8 탐색 (검색)
- **FR-SRCH-1** 위키 페이지에 대한 **하이브리드(BM25 + 벡터) 검색 엔진을 프로젝트 초기부터 도입**한다.
- **FR-SRCH-2** 키워드(BM25)와 의미(임베딩 벡터) 결과를 결합하고, 필요 시 LLM 재랭킹으로 정확도를 높인다.
- **FR-SRCH-3** 적재 시 위키 페이지를 검색 인덱스에 자동 반영(갱신/삭제 포함)한다.
- **FR-SRCH-4** 검색은 웹 UI 및 LLM 도구(백엔드 내부 호출) 양쪽에서 사용 가능해야 한다.

### 5.9 임베딩·VectorDB (과제 필수)
- **FR-VDB-1** 정규화·청킹된 문서/위키 청크를 **임베딩하여 VectorDB에 저장**한다.
- **FR-VDB-2** VectorDB는 다음 세 용도의 공통 기반으로 사용한다:
  (a) 하이브리드 검색의 벡터 부분(FR-SRCH), (b) 유사도 분석의 후보 추리기(FR-SIM-1),
  (c) **내용 보강** — 위키 작성/통합 시 의미적으로 관련된 기존 청크를 검색해 컨텍스트로 제공.
- **FR-VDB-3** 적재 시 임베딩·인덱스를 자동 갱신하고, 페이지 삭제·변경 시 동기화한다.
- **FR-VDB-4** 임베딩 모델·VectorDB 도구는 로컬/소규모 환경에서 운용 가능한 것으로 선택한다.

### 5.10 멀티 에이전트 워크플로우 & 시각화 (교육·발표 핵심)
- **FR-AGT-1** 핵심 작업을 **LangGraph 기반 오케스트레이터 + 전문 에이전트** 구조로 수행한다(§4.1).
- **FR-AGT-2** 각 에이전트의 **시작/진행/완료/실패 상태와 산출물·주요 결정**을 이벤트로 발행한다.
- **FR-VIZ-1** 프론트엔드에서 워크플로우 진행을 **단계 그래프(노드) 형태로 실시간 시각화**한다. (LangGraph 노드 상태를 노드 그래프로 매핑; 각 노드는 대기/진행/완료/실패 상태를 색·아이콘으로 표시)
- **FR-VIZ-2** 진행 중·완료 단계, 각 에이전트의 입력·출력, 소요 시간 등을 시연 가능하게 표시한다.
- **FR-VIZ-3** 백엔드는 진행 이벤트를 **SSE 또는 WebSocket**으로 스트리밍한다.
- **FR-VIZ-4** 위키 결과(생성/변경된 페이지, SDLC 단계별 현황)를 UI에서 조회할 수 있다.

## 6. 비기능 요구사항 (NFR)

- **NFR-1 (정확도)** 정제 정확도 80% 이상(수동 검증 기준). 의미 기반 병합은 **자동 수행하되 충돌·변경 지점을 표시**하여 사용자가 사후 검토·교정할 수 있게 한다.
- **NFR-2 (자동화)** 전체 문서 대비 자동 처리 비율 70% 이상.
- **NFR-3 (휴먼인더루프)** 단건 인터랙티브 적재 시 사용자가 단계별 진행·요약·갱신 내용을 확인하고 방향을 지시할 수 있어야 한다.
- **NFR-4 (비용/성능)** 모델 호출 비용·성능을 고려한다. 중간 규모(~100 출처, 수백 페이지)에서 검색·적재가 원활히 동작해야 한다.
- **NFR-5 (이식성)** 위키는 마크다운 파일의 git 저장소로 관리되어 버전 관리·브랜치·협업이 가능해야 한다.
- **NFR-6 (관찰성)** frontmatter 기반 메타데이터로 위키 구조·SDLC 단계별 현황을 웹 UI에서 조회할 수 있어야 한다.
- **NFR-7 (스택)** 백엔드는 Python, 프론트엔드는 React로 구현한다. (세부 프레임워크는 §11 참조)

## 7. 데이터·파일 규약

### 7.1 최상위 디렉토리
- `raw/` — 원본 출처(불변). 웹페이지 변환 md, 로컬 md 파일.
- `wiki/` — LLM 생성 위키 페이지(아래 SDLC 분류).
- `CLAUDE.md` — 스키마(위키 규약·워크플로).
- `index.md`, `log.md` — 카탈로그·타임라인.

### 7.2 위키 SDLC 분류 (Waterfall)
위키 산출물 페이지는 표준 Waterfall 단계 디렉토리로 분류한다. (단계명·세부 구조는 §10-Q1 확정에 따라 조정)

```
wiki/
  01-requirements/   요구사항 정의서, 유스케이스, 범위
  02-design/         아키텍처, 상세설계, API/DB 설계, 화면설계
  03-implementation/ 구현 가이드, 코드 설명, 컨벤션
  04-test/           테스트 계획, 테스트케이스, 결과
  05-deployment/     배포 절차, 환경 구성, 릴리스 노트
  06-operation/      운영 가이드, 트러블슈팅, 모니터링
  _entities/         교차 참조용 엔티티/개념 페이지(선택)
```

### 7.3 페이지 규약
- **frontmatter**: YAML로 `title`, `sdlc_phase`, `tags`, `updated`, `source_count`, `status` 등을 기록한다.
- **상호 링크**: 페이지 간 연결은 마크다운 위키 링크로 유지하며, 고아 페이지를 만들지 않는다.
- **이미지(선택)**: 필요 시 로컬(`raw/assets/`)에 저장하여 URL 의존을 제거한다.

## 8. 범위 및 제약사항

### 8.1 In Scope
- 웹페이지 수집, **로컬 md 파일(Confluence 대체) 수집**
- 문서 정규화·병합, LLM 기반 유사 문서 그룹화
- SDLC 단계별 위키 페이지 생성·유지·상호 참조 관리
- 하이브리드(BM25+벡터) 검색
- 웹 앱(Python 백엔드 + React) UI

### 8.2 Out of Scope
- **Confluence 직접 연동/인증** (이번 개발 범위 제외, 로컬 md로 대체)
- **사용자 인증/권한 관리** (로컬·단일 사용자 전제)
- **웹페이지 크롤링** (단건 URL 수집만 지원)
- 일괄 자동 적재 (단건 인터랙티브 우선; 추후 확장 가능)
- 실시간 협업 문서 편집 기능
- 완전 자동 의사결정 시스템(충돌은 자동 병합 후 표시·사후 검토)

### 8.3 제약사항
- HTML 구조 다양성으로 인한 파싱 난이도
- 의미 기반 병합 시 오판 가능성
- 초기 데이터셋 부족
- 모델 비용·성능 고려 필요

## 13. UI 화면 명세

> 시각화가 과제 핵심이므로 화면 요구를 구체화한다. 공통: 좌측 네비게이션 + 상단 상태바.

### 13.1 워크플로우 뷰 (핵심)
- **목적**: 적재 실행 중 멀티 에이전트 노드 그래프를 실시간 표시(React Flow).
- **요소**: 노드(§4.1 파이프라인) + 엣지, 노드별 상태 색/아이콘(대기·진행·완료·실패·입력대기),
  진행 애니메이션, 노드 클릭 시 입력·출력·소요시간·산출물 패널, 전체 run 타임라인/로그.
- **상호작용**: 노드 선택 상세 보기, run 재실행/재개, `awaiting_input` 시 승인 버튼.
- **데이터**: §4.2 SSE 이벤트 구독.

### 13.2 적재 / 소스 입력 뷰
- **목적**: 단건 인터랙티브 적재 시작.
- **요소**: URL 입력, 로컬 md 업로드, 적재 시작 버튼, 진행 시 워크플로우 뷰로 연결.
- **상호작용**: 단계별 결과 확인, 사용자 방향 지시(HITL).

### 13.3 위키 뷰어 + 검색 뷰
- **목적**: SDLC 단계별 위키 페이지 탐색·열람·검색.
- **요소**: SDLC 단계별 페이지 목록(트리/사이드바), 페이지 본문 렌더(마크다운·frontmatter·백링크),
  하이브리드 검색 박스(결과 + 출처/단계 표시), 위키 지식그래프(React Flow, 페이지=노드·링크=엣지).
- **상호작용**: 위키링크 따라가기, 그래프 노드 클릭→페이지 열기, 검색→페이지 점프.

### 13.4 충돌 / diff 뷰
- **목적**: 자동 병합(Q14) 결과의 충돌·변경 지점 사후 검토.
- **요소**: 병합 전/후 diff, 충돌 블록 하이라이트, 출처 표기, 수락/되돌리기 액션.
- **상호작용**: 충돌 항목 단위 검토, 페이지로 이동.

## 14. 데이터 모델 · 스키마

> [omegawiki-reuse.md](./omegawiki-reuse.md)의 `runtime/schema/*.yaml` 데이터 주도 방식을 차용하여,
> 엔티티/엣지/규약을 YAML로 정의한다.

### 14.1 페이지 타입
- **SDLC 산출물 페이지** (`wiki/0N-*/`): 단계별 산출물(요구사항서·설계서·테스트케이스 등).
- **엔티티/개념 페이지** (`wiki/_entities/`): 여러 단계에 걸쳐 참조되는 용어·컴포넌트·개념(교차 참조 허브).

### 14.2 Frontmatter 스키마
공통 필드:
```yaml
title:        # 페이지 제목
slug:         # 소문자-하이픈, ^[a-z0-9]+(-[a-z0-9]+)*$
type:         # deliverable | entity
sdlc_phase:   # requirements|design|implementation|test|deployment|operation (deliverable일 때)
tags:         []
status:       # draft | active | superseded
updated:      # ISO8601
source_count: # 통합된 원본 출처 수
sources:      []  # 원본 raw 경로/URL 목록
```

### 14.3 그래프 엣지 타입 (`wiki/graph/edges.jsonl`)
`{ from, to, type, confidence, evidence }` 형식. 주요 타입:
`references`(참조), `duplicate_of`(중복), `merged_from`(병합 출처), `supersedes`(대체),
`conflicts_with`(충돌), `relates_to`(연관). → FR-SIM·FR-MERGE에 활용.

### 14.4 청킹 전략
- **분할 기준**: 마크다운 헤딩(구조) 우선 + 토큰 길이 보조(약 512~1024 토큰, 중첩 ~15%).
- **단위**: 청크는 `{ page_slug, chunk_id, sdlc_phase, text }`로 식별.

### 14.5 임베딩 / Chroma 구조
- **모델**: OpenAI `text-embedding-3-small`(기본; 필요 시 `-large`).
- **컬렉션**: 단일 컬렉션 + 메타데이터(`page_slug`, `chunk_id`, `sdlc_phase`, `source`, `updated`)로 필터.
- **동기화**: 페이지 생성/변경/삭제 시 해당 청크 벡터 upsert/delete(FR-VDB-3).

## 15. 유스케이스 & 데모 시나리오

### 15.1 유스케이스
- **UC-1 단건 적재**: 사용자가 URL/로컬 md 입력 → 파이프라인 실행 → SDLC 단계별 위키 페이지 생성.
- **UC-2 중복/유사 병합**: 유사 문서 적재 시 similarity가 후보 탐지·LLM 판정 → 자동 병합 + 충돌 표시.
- **UC-3 검색**: 하이브리드 검색으로 관련 페이지 탐색.
- **UC-4 질의**: 위키 대상 질문 → 관련 페이지 종합 + 인용 답변, 가치 있는 결과는 페이지로 누적.

### 15.2 데모 시나리오 (전체 엔드투엔드, Q19)
발표용 핵심 흐름. 워크플로우 뷰에서 노드 진행이 실시간으로 보이는 것이 시연 포인트.
1. **적재**: 문서 A(URL 또는 md) 적재 → fetch→…→index 노드가 순차 점등, 위키 페이지 생성.
2. **병합 시연**: 문서 A와 유사한 문서 B 적재 → similarity 노드가 후보·중복 판정 → merge 노드가
   자동 통합 → **충돌/diff 뷰**에서 변경·충돌 지점 확인.
3. **검색**: 하이브리드 검색으로 통합된 내용을 키워드/의미로 탐색(VectorDB 활용 부각).
4. **질의**: 위키에 질문 → 인용 기반 답변 생성, 결과를 새 페이지로 누적.

→ 이 4단계를 끊김 없이 보여 주는 것을 데모 성공 기준으로 한다(KPI 정량치는 실습 규모에서 보조 지표).
